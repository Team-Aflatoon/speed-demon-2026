A later candidate, c16 (row 52, local measurements only, box runs pending), keeps its design with three instruction cuts in the join and the name lookup: 3.06% fewer instructions (1.1511 G), S 609. It is v14 (row 50) with a smaller source and an AES-NI name hash; v14 is v13's (row 49) program with the distinct-name count changed from exact names to a 62-bit hash identity and one shared bit matrix. The build needs AES-NI and PCLMULQDQ, checked at compile time only.

Before them: v13 is v10 (commit 501b40f; 26.6 ms, 16.0 MB, K 32.32, S 793, run-43decb69e8ce) with its code laid out so that default rustfmt splits fewer lines (S 793 to 755, instructions +0.78%). v5 (a clean-room rework of v4.2 that ran 37.4 ms, run-41dfe519e529) kept private (id, group) pairs and counted them after a barrier; v6 to v10 cut instructions by 16.3%, 5.9%, 7.0% and 0.8% in turn. PERF.md has every step with its board run, the builds we tried and rejected (lazy arenas, a clean-room rewrite, a memory study) and v4's race (a wrong output in about 1 run of 100, found by a stress test and fixed in v4.1). It also has a correction: we first blamed the box's name cost on the atomic OR on a shared bitset, which is what v5 was built to avoid, but the probe removed all name work at once, and the shared OR costs about 2 ms in v14 (row 50 notes).

The public AVENGERS (github.com/Mukul07777/speed-demon-2026; C 24.0 ms, 8.6 MB) and Cache Me (github.com/manusingh090/speed-demon-2026-entry; 22.8 ms, 8.5 MB) entries are faster and leaner than ours; we studied how their name hash, bit matrix and huge pages work and wrote our own code, copying none of theirs.

## Approach

A Rust binary with no crates, built as a static executable for x86-64-v3 (AVX2, BMI2, SSE4.2); the flags are in `.cargo/config.toml`, so a plain `cargo build` gives the same binary, and the crate refuses to compile without AVX2. The quote prefix XOR uses PCLMULQDQ and the name hash AES-NI; x86-64-v3 includes neither, but every CPU that has AVX2 has both, so `.cargo/config.toml` adds `+aes` and `+pclmulqdq` and the crate refuses to compile without them (there is no run-time check). Up to twelve worker threads (started as a binary tree, the main thread being worker 0) parse `records.csv` in parallel, and the result is exact for any input that follows the grammar in spec section 2.1, not only for what the generator writes. A record is parsed, joined and counted in one pass: there is no second phase.

**Input** (`run.rs`, `main.rs`).

- `records.csv` is read with `pread` in pieces of 64 KiB, each worker into one reusable buffer of its own, and each piece is parsed while it is still in the core's cache; the small `regions.csv` is memory-mapped read-only. Not mapping `records.csv` was faster on the scoring box (PERF.md, rows 32 and 33).
- A worker's chunk is nominally the 64 KiB from `c * 65536`; it reads that plus 1 KiB of slack, and its real start and end are the first record boundaries (see below) at or after the nominal start and end. Both cuts are computed from the file's bytes alone, so two neighbouring chunks always agree on the cut between them.
- If a record runs past the slack, the read doubles until the end is found, so records of any length work, and a record longer than a whole piece simply leaves the chunks it covers empty.
- After a chunk's bytes the buffer holds 128 zero bytes, so the parser can always load whole 64-byte blocks.
- Huge pages are asked for (`MADV_HUGEPAGE`) for one mapping only, the name table and matrix. Every other anonymous mapping, the region map being the only large one, is marked `MADV_NOHUGEPAGE`, so that a kernel that hands out huge pages to everything cannot charge 2 MiB for a sparse map.

**Parsing with bitmasks** (`parse.rs`). For each 64-byte block, AVX2 compares give one bit per byte for `"`, `,` and LF. In this grammar a byte is inside a quoted field exactly when an odd number of quote bytes come before it: a `""` escape simply closes and reopens. So the prefix XOR of the quote mask (one carry-less multiply) is the in-quotes mask, and the commas and LFs outside it are the separators. Their offsets are flattened in order into one list, the first seven of a block written without a branch, so a record's separators are simply the next five: its four commas and its terminator. Records are handled in windows of 4 KiB, in three loops: `scan` makes the masks and the list, `parse` reads each record's fields independently of the others and starts loading the region-map byte and the name-table line the record needs, and `join` does the join, the aggregates, the name lookup and the setting of the pair's matrix bit, by which time most of those cache misses have overlapped. A record's three numbers (id, region id and amount) are loaded from their field starts into one AVX2 register, range-checked and converted together: an id and a region id of up to 8 digits and an amount of up to 5 before the dot; anything else takes a cold byte-at-a-time path. The text fields need no parsing: a record's text bytes (name plus note) are its width minus its delimiters minus half its quote count, the quotes counted from per-block counts and masks. A record's name bytes come the same way, from the quotes counted in its name field (its raw length less half of them, the delimiting pair excepted), and note bytes are the difference. A BOM is skipped where 2.1 allows it, at the start of a record.

**Grammar checks.** Every record must be four commas and an LF outside quotes, with valid digits between them (a CR must come right before its LF); the LFs outside quotes must number exactly the records, which proves that the first four separators of every record were commas. A quote placed where 2.1 forbids it, inside an unquoted field, is not diagnosed. A failure is reported with the byte offset of the record, and a non-zero exit (see the fallback below).

**Splitting the file safely** (`run.rs`). Chunks are cut just after an LF that is followed by a digit or a BOM byte. By spec 2.2 no quoted value contains a digit or a non-ASCII byte, so such an LF ends a record. That is a guess, and it is checked, not trusted. Every chunk is parsed as if it started outside quotes and counts its quote bytes. Since "inside quotes" means "an odd number of quotes so far", once every chunk has an even number of quotes in the chunks before it, every chunk did start outside quotes right after a terminator, and was parsed exactly as one sequential pass would have parsed it. If the check fails, or any chunk breaks the grammar, `main` runs the whole file again with a single chunk, which starts at the start of the file and so is always right, and says so on stderr (`chunk cuts unproven; reparsing as one chunk`). A grammar error there is reported as `records.csv breaks spec 2.1 at N`, with exit status 1.

**Start-up** (`run.rs`). Before records start there are small tasks: faulting in the two huge pages of the table and matrix, one task each (`MADV_POPULATE_WRITE`), then parsing 32 pieces of `regions.csv`. Whichever workers are up first claim them, so workers wait only for these tasks, not for the last thread to start; a late thread just joins in. No worker touches the mapping before both pages are faulted in: huge pages that several workers touch at once are each charged 2 MiB again (PERF.md, row 15).

**Joining** (`run.rs`). `regions.csv` becomes a map from region id to a dense group number (0 is `_UNMATCHED`), one byte per id, sized by the id on the file's last line (the largest, by spec 2.3). A region id past the map is clamped to a final 0 entry, so a lookup never branches. Any line that is not `id,CCC` stops the program with its byte offset.

**Distinct names** (`names.rs`). Names are not stored, and no per-record log is kept: one shared table gives each name a dense id, and one shared bit matrix says which (country, name) pairs have been seen.

- A name is identified by a 64-bit hash of its raw (still escaped) bytes and its length. The first 32 bytes of the name, the rest zeroed by a mask, go through three AES rounds (AES-NI) keyed by the length; a longer name (about 1 record in 5,000) goes on, out of line, 32 bytes at a time, each block keyed by the hash so far. The empty unquoted name and `""` both have length 0 and one hash. 14 bits of the hash choose a bucket and 47 are stored as the name's tag: two different names merge only if they agree on all 61 bits. **That is a trade against v13, which compared the bytes**: for the spec's pool of 100,000 names the chance that any pair agrees is about 2.2e-9 per dataset (PERF.md, "Hash identity"). The hash is fixed and unseeded, so a dataset gives the same output on every run.
- The table is 2^15 buckets of 8 one-word slots, one cache line each (2 MiB). A slot is 0, or `tag << 17 | (id + 1)`, and changes once, by compare-and-swap. A lookup compares the 8 tags of its home bucket with two AVX2 loads and no branch, which finds the name for almost every record; the rest (a first sight, or a name that overflowed to another bucket) go to a cold function that walks the buckets and claims the first empty slot. A new name takes the next id of its worker's block of 64, reserved with one `fetch_add` on a counter that has a cache line to itself.
- The matrix has a row of 102,400 bits (1,600 words) for each of the 241 groups (2.9 MiB), bit `id` of row `group`. After the lookup, a record starts loading its bit's cache line for writing (`PREFETCHW`) and goes on to the next record; a second loop over the batch then sets the bits with an atomic OR, compiled to `lock bts`, which reports the bit's old value: a clear bit is a new distinct name for that group and is counted there and then. A group's distinct count is thus a sum, and the rows are never read.
- Memory: the table (1 MiB) and matrix are one 3.94 MiB mapping on two huge pages, against v13's 3 MB table and 7.3 to 7.9 MB of pair arenas. Nothing in it grows with the scheduling: every size is fixed.
- Race-freedom: a slot goes from 0 to its final value in one compare-and-swap and is never written again, so a reader sees it empty or whole. Two workers inserting one name walk the same slots in the same order and meet at the first slot either claims, so a name is never inserted twice; an id is spent only by a successful swap, and the blocks are disjoint, so no id names two names; each (group, name) bit is set by an atomic OR, and exactly one OR sees it clear. The one place that relies on the hardware instead of Rust's memory model is the AVX2 read of a bucket: an aligned 8-byte lane is read whole on x86, so it is 0 or final, and a hit's id is read again through the atomic slot (names.rs has the argument).

**Waiting.** Workers wait once, and the wait yields the CPU instead of spinning, so a crowded machine can run the workers still busy: at the start, for the start-up tasks. Everything else is claimed: chunks.

**Aggregates.** Each worker keeps its own id sum, amount sum, text bytes, min, max, name bytes, and records and distinct names (two halves of one word), per group; they are summed at the end, sorted by country code, and printed with integer cents formatting. The note bytes are the text bytes minus the name bytes. `_UNMATCHED` comes last, and groups with no records are not printed.

**Limits, all far above the spec.** The name table and matrix are fixed: 2^14 buckets of 8 slots and 102,400 dense ids, which are handed out to workers in blocks of 64, so about 101,000 distinct names fit (the spec's pool is 100,000; a longer name is hashed whole, so its length does not matter). Beyond that the program stops with `more than about 102,000 distinct names` and exit 1; there is no retry with a bigger table. Up to 240 countries, as spec 2.3 lists (`regions.csv: more than 240 countries` beyond), a last region id up to 2^27 (a larger one is rejected with its byte offset), and files under 4 GiB (the parser's offsets are 32-bit); beyond those the program says so on stderr and exits non-zero. Numbers of more than 8 digits only take the slow path; a value past u64::MAX saturates at u64::MAX, so a huge region id is simply unknown, as the reference treats it.

**Testing.**

- **The repository's suite.** `tests/run.sh` (in the repository root) builds each track's image and runs it as the scoring harness does (no network, read-only root, `/data` read-only, user nobody, pinned CPUs), comparing the output byte for byte. It has 33 end-to-end cases over the four tracks, 9 of them for this track: the spec's worked example, an edge case (a BOM inside quotes, no final terminator), tiny seeds 1 and 2, and five malformed inputs that must exit 1 (a bad amount, an extra field, an LF in place of a comma, an LF inside a record, a missing field). Their expected outputs come from the organisers' reference implementation. `bash tests/run.sh c` runs just this track.
- **External checks, recorded in PERF.md (rows 50 and 51).** The full-size seeds 1, 7, 101 and 202, a 50-case fuzz, the 300 + 300 differential against the parent version, forced single-chunk and long-name cases, and the stress runs for races. The table below lists them; the synthetic inputs were written by small scripts from the spec's grammar, and the scripts and files are not kept in this repository. Every check compares the output byte for byte with the reference (or with the previous version, where it says so).
- **One known divergence.** A quoted amount (`"12.50"`) is rejected with exit 1, where the reference accepts it. The generator never quotes an amount (spec 2.2), so it cannot occur in the scored inputs.
- The official tests are in the organisers' repository (`tests/test_c_join.py` there). Each version was also compared with its parent on 300 mutated inputs (random comma, quote, LF, CR and BOM edits, with and without a final terminator, 129 of them valid) and 300 inputs with odd numbers (9-digit ids, huge region ids, leading zeros, bad amounts; 68 valid): all identical in exit status and output. Debug builds (assertions, overflow checks, every unchecked read asserted) passed the four seeds for v14 and c15, and all the cases for v13.

## Dependencies

None. The two libc functions used, `mmap` and `madvise`, are declared by hand with `extern "C"`; `pread` comes from the standard library (`FileExt::read_exact_at`), as does everything else.

## With another 24 hours

- Instructions are about 358 per record in c15 (1.1874 G for the 3.32 M records of seed 1, cachegrind, one thread; v13 had 367 and v14 372) and spread thin: about 150 in `parse`, 91 in `scan`, 83 in `join`, 27 in phase 2 and 14 in slow probes (the split measured on v9, which has the same code as v13 in those loops; v14 and c15 have no phase 2, and c15's cheaper hash is most of its 3.9% under v14). Each further 50 lines of S would need dropping one of the generic 2.1 record path, the one-chunk fallback or the long-slot table. A SIMD number path for several records at once could save at most about 3 instructions a record, for the shuffling across records.
- Memory: the box reads 8.7 MB for a process that does nothing (PERF.md, probe ladder). c15's own memory is the 6 MiB table and matrix (c16, PERF.md row 52, trims them to 3.94 MiB on two huge pages), the 1 MB region map and about 1.5 MB of per-worker buffers. Smaller steps are a table of 2^14 buckets of full 64-bit hashes (1 MiB, with the region map moved onto the same huge pages), the region map as a rank bitmap (about 0.4 MB instead of 1 MB), and mapping `records.csv` with `MADV_DONTNEED` per finished piece instead of twelve read buffers; none is measured.
- About 3 ms of the run is setup (PERF.md, probe ladder). Moving it off the critical path won 2.7% locally but lost on the box (row 46), so a next attempt would be measured there first. S could drop further: rustfmt explodes every struct literal over 18 characters.
- Keep measuring on the scoring box: its probes (PERF.md) showed that local timings, taken on a faster laptop that was shared with other jobs, mispredicted which changes would help, in both directions.

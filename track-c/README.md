## Result

The current version, v13 (commit 2938130, PERF.md row 49), measured on the board as run-91c3366ba4bb: T 26.8 ms, M 16.0 MB, K 32.47 (75.58 points). S 755, D 1 (no crates). A second run, run-c1288ccc234f, gave 26.9 ms, 16.1 MB, K 32.37 (75.51 points). The reference is 14.44 s and 367 MB. M (bytes / 10^6) is mostly the program's own tables and buffers (see **Distinct names**); the rest is code, stacks and the container runtime's processes, charged before `main` runs: a process that exits at once already reads 8.7 MB on the box (run-6330bbe72613).

v13 is v10 (commit 501b40f; 26.6 ms, 16.0 MB, K 32.32, S 793, run-43decb69e8ce) with its code laid out so that default rustfmt splits fewer lines, and regions.csv mapped read-only: S 793 to 755 for 0.78% more instructions. Before them, v5.2 (run-52c515f71c76) ran 32.4 ms, 16.7 MB, K 28.60 at S 882, so the last day's work (v6 to v13: fewer instructions per record, then fewer lines) is 5.6 ms faster, 0.7 MB smaller and 127 lines shorter. The design of v5 (a clean-room rework of v4.2 that ran 37.4 ms, run-41dfe519e529) is unchanged; v6 to v10 cut instructions by 16.3%, 5.9%, 7.0% and 0.8% in turn (cachegrind, one thread, seed 1: 1.661 G to 1.210 G). Of the 26.6 ms of v10, the probe ladder in PERF.md puts about 3 ms in setup and about 22 ms in record work. PERF.md has every step with its board run, the builds we tried and rejected (lazy arenas, a clean-room rewrite, a memory study) and v4's race (a wrong output in about 1 run of 100, found by a stress test and fixed in v4.1).

| File | What it does |
|---|---|
| `src/main.rs` | Arguments, the fallback to one chunk, output formatting, `die`, and the three kernel calls (`mmap`, `madvise`, `prctl`) declared by hand |
| `src/run.rs` | Threads, start-up tasks, the regions.csv map, chunk claiming, pread and the chunk cuts, the quote-parity proof, the two phases |
| `src/parse.rs` | The records.csv parser: AVX2 masks, the separator list, grammar checks, field parsing, windows of records |
| `src/names.rs` | The shared name table (phase 1) and the per-worker pair arenas with the counting (phase 2) |

Usage: `track-c [DATA_DIR [OUT_DIR]]`, by default `/data` and `/out` (the harness passes none). Errors go to stderr with exit status 1; the one fallback (to a single chunk) prints a note on stderr and still exits 0.

## Approach

A Rust binary with no crates, built as a static executable for x86-64-v3 (AVX2, BMI2, SSE4.2); the flags are in `.cargo/config.toml`, so a plain `cargo build` gives the same binary, and the crate refuses to compile without AVX2. The quote prefix XOR uses PCLMULQDQ, which x86-64-v3 does not include, so `main` checks for it at start-up and exits with a message on a CPU without it. Up to twelve worker threads (started as a binary tree, the main thread being worker 0) parse `records.csv` in parallel, and the result is exact for any input that follows the grammar in spec section 2.1, not only for what the generator writes. The work has two phases: phase 1 parses and joins, and phase 2, after one barrier, counts distinct names.

**Input** (`run.rs`, `main.rs`).

- `records.csv` is read with `pread` in pieces of 64 KiB, each worker into one reusable buffer of its own, and each piece is parsed while it is still in the core's cache; the small `regions.csv` is memory-mapped read-only. Not mapping `records.csv` was faster on the scoring box (PERF.md, rows 32 and 33).
- A worker's chunk is nominally the 64 KiB from `c * 65536`; it reads that plus 1 KiB of slack, and its real start and end are the first record boundaries (see below) at or after the nominal start and end. Both cuts are computed from the file's bytes alone, so two neighbouring chunks always agree on the cut between them.
- If a record runs past the slack, the read doubles until the end is found, so records of any length work, and a record longer than a whole piece simply leaves the chunks it covers empty.
- After a chunk's bytes the buffer holds 128 zero bytes, so the parser can always load whole 64-byte blocks.
- `prctl(PR_SET_THP_DISABLE)` runs first: a huge-page fault can stall while the kernel compacts memory.

**Parsing with bitmasks** (`parse.rs`). For each 64-byte block, AVX2 compares give one bit per byte for `"`, `,` and LF. In this grammar a byte is inside a quoted field exactly when an odd number of quote bytes come before it: a `""` escape simply closes and reopens. So the prefix XOR of the quote mask (one carry-less multiply) is the in-quotes mask, and the commas and LFs outside it are the separators. Their offsets are flattened in order into one list, the first seven of a block written without a branch, so a record's separators are simply the next five: its four commas and its terminator. Records are handled in windows of 4 KiB, in three loops: `scan` makes the masks and the list, `parse` reads each record's fields independently of the others and starts loading the region-map byte and the name-table line the record needs, and `join` does the join, the aggregates, the name lookup and the pair append, by which time most of those cache misses have overlapped. A record's three numbers (id, region id and amount) are loaded from their field starts into one AVX2 register, range-checked and converted together: an id and a region id of up to 8 digits and an amount of up to 5 before the dot; anything else takes a cold byte-at-a-time path. The text fields need no parsing: a record's text bytes (name plus note) are its width minus its delimiters minus half its quote count, the quotes counted from per-block counts and masks. Name bytes come from phase 2 and note bytes are the difference. A BOM is skipped where 2.1 allows it, at the start of a record.

**Grammar checks.** Every record must be four commas and an LF outside quotes, with valid digits between them (a CR must come right before its LF); the LFs outside quotes must number exactly the records, which proves that the first four separators of every record were commas. A quote placed where 2.1 forbids it, inside an unquoted field, is not diagnosed. A failure is reported with the byte offset of the record, and a non-zero exit (see the fallback below).

**Splitting the file safely** (`run.rs`). Chunks are cut just after an LF that is followed by a digit or a BOM byte. By spec 2.2 no quoted value contains a digit or a non-ASCII byte, so such an LF ends a record. That is a guess, and it is checked, not trusted. Every chunk is parsed as if it started outside quotes and counts its quote bytes. Since "inside quotes" means "an odd number of quotes so far", once every chunk has an even number of quotes in the chunks before it, every chunk did start outside quotes right after a terminator, and was parsed exactly as one sequential pass would have parsed it. If the check fails, or any chunk breaks the grammar, `main` runs the whole file again with a single chunk, which starts at the start of the file and so is always right, and says so on stderr (`chunk cuts unproven; reparsing as one chunk`). A grammar error there is reported as `records.csv breaks spec 2.1 at N`, with exit status 1.

**Start-up** (`run.rs`). Before records start there are small tasks: parsing 32 pieces of `regions.csv`, then faulting in 32 shares of the name table. Whichever workers are up first claim them, so workers wait only for the region map, not for the last thread to start; a late thread just joins phase 1. Each worker then reserves its pair arena and faults in the expected share of it (the file's size over 64 bytes, over the workers) with one `MADV_POPULATE_WRITE`.

**Joining** (`run.rs`). `regions.csv` becomes a map from region id to a dense group number (0 is `_UNMATCHED`), one byte per id, sized by the id on the file's last line (the largest, by spec 2.3). A region id past the map is clamped to a final 0 entry, so a lookup never branches. Any line that is not `id,CCC` stops the program with its byte offset.

**Distinct names** (`names.rs`). The shared hash table and the per-worker arenas keep the hot path from ever writing a cache line another core reads.

- Phase 1, while parsing: every name is interned in one shared lock-free table, and its slot index is its id. After the first few percent of the file nearly every name is already there, so the table is read-mostly. The record then appends its (id, group) pair, 16 bits, to a bucket in its own worker's arena: bucket `id >> 8`, entry `group << 8 | id & 255`. A bucket is a chain of 128-byte blocks (two cache lines: a 32-bit link and 62 entries), taken from the worker's own lazily backed arena, so these are private stores to a few hot lines.
- Phase 2, after one barrier: workers claim buckets. A bucket's pairs from all arenas are counted against an 8 KiB bitset (256 ids x 256 groups) that stays in L1, four entries at a time, and each entry also adds its record and its name's unescaped length to its group. A group's distinct pairs are the popcount of its 256 bits, which is also how the bitset is cleared for the next bucket.
- The table has two arrays. Short names (at most 15 raw bytes, 87% of the records' names) take 16-byte slots, four to a 64-byte line: the first name word and a `meta` word holding the tag (length + 1) and bytes 8 to 14 XORed with a mix of the first word, so that `meta` alone tells the names of a line apart while the bytes stay recoverable. A short name's home is a whole line, which a lookup compares branch-free (four Acquire loads of `meta` and a chain of conditional moves) and where it finds the name for 89% of records on seed 1; overflow goes to lines an odd `step` apart, not to the next line, so there are no runs of full lines. Names of 16 to 24 bytes take 32-byte slots of three name words and `meta`, probed linearly. Names over 24 bytes (about 1 record in 5,000) are interned under a lock in a hash map. Raw (still escaped) bytes are the key, which works because escaping is one-to-one, and the empty unquoted name and `""` both have length 0. The hash only chooses where to look; the bytes are always compared.
- A worker claims an empty slot by a compare-and-swap of `meta` from 0 to a FILLING marker, writes the name words, and publishes with one release store of the final `meta`. `meta` changes only through those two operations, and every reader loads it with acquire before reading the words, so a lookup that sees a published slot sees the whole name. A lookup that finds FILLING waits for the store.
- Memory: the name table is 3 MB (2 MiB of short slots and 1 MiB of long ones) and the pair arenas about 6.6 MB at 2 bytes per record, against v4.2's 4.2 MB table and 3.7 MB bitset. That is the price of v5's speed (PERF.md): 4.6 MB more on the board, K 5.6% higher.

**Waiting.** Workers wait twice, and both waits yield the CPU instead of spinning, so a crowded machine can run the workers still busy: at the start, for the start-up tasks, and once at the end of phase 1. Everything else is claimed: chunks in phase 1 and buckets in phase 2.

**Aggregates.** Each worker keeps its own id sum, amount sum, text bytes, min and max per group, and phase 2 yields records, distinct names and name bytes per group; they are summed at the end, sorted by country code, and printed with integer cents formatting. The note bytes are the text bytes minus the name bytes. `_UNMATCHED` comes last, and groups with no records are not printed.

**Limits, all far above the spec.** The name table is fixed: 2^17 short slots and 2^15 long ones (room for 131,072 short names and 32,768 of 16 to 24 bytes, where the spec's pool of 100,000 names is about 87% short) and 16,384 names over 24 bytes. If one of them fills, the program stops with `more distinct names than the name table holds` or `more than 16,384 distinct names over 24 bytes` and exit 1; there is no retry with a bigger table (v7 dropped it for S; PERF.md row 42). Up to 255 countries (`regions.csv: over 255 countries` beyond), a last region id up to 2^27 (a larger one is rejected with its byte offset), and files under 4 GiB (the parser's offsets and name tags are 32-bit); beyond those the program says so on stderr and exits non-zero. Numbers of more than 8 digits only take the slow path; a value past u64::MAX saturates at u64::MAX, so a huge region id is simply unknown, as the reference treats it.

**Testing.** The official tests live in the organisers' repository (`tests/test_c_join.py` there, not in this one). Every check below compares the output byte for byte with the reference, unless it says otherwise. The synthetic inputs were written by small scripts that build records.csv and regions.csv from the spec's grammar; the scripts and files are not kept in this repository. Each version was also compared with its parent on 300 mutated inputs (random comma, quote, LF, CR and BOM edits, with and without a final terminator, 129 of them valid) and 300 inputs with odd numbers (9-digit ids, huge region ids, leading zeros, bad amounts; 68 valid): all identical in exit status and output. A debug build (assertions, overflow checks, every unchecked read asserted) passes the same cases.

| Case class | Inputs | Path exercised |

| Full scale | seeds 1, 7, 101 and 202 (each 3 times at 12 threads and once on one CPU) | the normal parallel path |

## Dependencies

None. The three libc functions used, `mmap`, `madvise` and `prctl`, are declared by hand with `extern "C"`; `pread` comes from the standard library (`FileExt::read_exact_at`), as does everything else.

## With another 24 hours

- Instructions are about 367 per record (1.2194 G for the 3.32 M records of seed 1, cachegrind, one thread) and spread thin: about 150 in `parse`, 91 in `scan`, 83 in `join`, 27 in phase 2 and 14 in slow probes (the split measured on v9, which has the same code). Each further 50 lines of S would need dropping one of the generic 2.1 record path, the one-chunk fallback or the long-slot table. A SIMD number path for several records at once could save at most about 3 instructions a record, for the shuffling across records.
- Memory: the box reads 8.7 MB for a process that does nothing (PERF.md, probe ladder), and v13 reads 16.0 MB. The pair arenas are 7.3 to 7.9 MB, the name table and region map 4.1 MB. A study of what is cuttable without speed risk (PERF.md row 48) found only 0.3 to 0.4 MB; halving the long-name table would leave 1.26x headroom over the 13,053 long names of seed 202 and was rejected. The region map could be a rank bitmap (about 0.4 MB instead of 1 MB).
- About 3 ms of the run is setup (PERF.md, probe ladder). Moving it off the critical path won 2.7% locally but lost on the box (row 46), so a next attempt would be measured there first. S could drop further: rustfmt explodes every struct literal over 18 characters.
- Keep measuring on the scoring box: its probes (PERF.md) showed that local timings, taken on a faster laptop that was shared with other jobs, mispredicted which changes would help, in both directions.

# Track C: performance log

Every step from the reference to your final version, each with the live-board run ID that measured it. Judges check that the run IDs exist and that each change moved the way you say it did.

Rows with a Run ID are board measurements. All other T and M are **local** (i7-14650HX, Docker Desktop, `--cpuset-cpus=0-11`, the bench script that mirrors the harness); the board box was about 1.6x slower than this machine when quiet. The local machine was shared with other heavy benchmark jobs during this work, so single runs varied by up to 2x. Small changes were therefore compared by interleaving runs of the two builds (A/B) and taking medians of wall time and of total CPU time (`perf stat` task-clock), which is far less sensitive to the other jobs. Hardware counters are not available in this VM. "CPU 1t" means one worker on one core.

Lessons:

- Parsing field by field is latency-bound: each field's position depends on the previous one. Bitmasks first, then fields, roughly halved parse cost per byte. Moving the remaining branches out of the separator loop gained less (about 10%).
- With twelve threads the expensive thing is not computing, it is cache lines that move between cores: atomics on lines other cores read, counters next to read-mostly fields, and first touches of shared pages.
- Lockstep rounds and bounded queues both turn one slow or descheduled worker into a stall for everyone. Unsynchronised sharing with atomics is slower per operation but never waits.
- Under a noisy machine only interleaved A/B runs and CPU time told real changes from noise.
- Most of what remains is memory latency, not instructions: three random lines per record (region map, name slot, group bits) and an atomic OR. Prefetching already hides what it can; only a sparser table measurably helped, at a memory cost.
- Peak memory starts at about 5 MB before `main` runs: the container runtime's own processes are charged to the same cgroup. Our own use is about 7.5 MB (4 MB name table, 3.7 MB pair bitset, 1 MB region map) plus page tables; the pair bitset is near the floor for exact distinct counting, so M moved little.
- The atomic OR on the shared pair bitset looked like the main remaining parallel cost in the profile, but swapping in a racy plain load and store (for timing only) saved just 7% of CPU (A/B 267 vs 248 ms), and dropping the update entirely 249 ms. Owner-private bitsets fed by queues could win at most that, so the shared atomic version stays: it never makes one worker wait for another.

# Team Aflatoon · Speed Demon 2026

Our entry for [Speed Demon 2026](https://speeddemon.dev), the 72-hour performance championship by Hackathon Raptors: take a deliberately naive Python reference, keep its output byte for byte, and make it as fast and as lean as we can on the organisers' scoring machine.

We entered all four tracks. Each one is a standalone Rust program with **no dependencies** beyond the standard library, built offline from its own folder. Our presentation is in [`docs/PRESENTATION.md`](docs/PRESENTATION.md).

## Nov 2: what changed on the last day

At 07:31 UTC the board had us 20th overall at 79.25 (A 84.8, B 77.5, C 75.7; D's 70.6 is not counted in the best three). Two waves of changes went in during the day, each decided on interleaved board runs against the production build in the same session. After the first wave, `bench/overall.py` showed us 19th at 80.50 at 10:58 UTC (best run per track 84.9, 78.8, 78.0); after the second, at 11:57 UTC, 19th at 80.66 (84.9, 79.0, 78.2). Both are standings from single runs, not a final score. The experiment log with every run ID is the "Nov 2" part of each track's `PERF.md`.

**First wave (adopted by 10:31 UTC)**

- **A v13 (S 447): a cap on how far parsing runs ahead.** The final score takes the **maximum** memory of the five runs and the mean of the middle three times (`harness/run_submission.py`). A's v9 read 21.1 to 22.1 MB instead of about 17 MB in 5 of its 27 runs in the public history (Nov 1 13:26 UTC to Nov 2 09:19 UTC), so one batch of five would probably have held a spike worth about 1 point. A thread descheduled while it holds the oldest unparsed piece stops the reports and the other threads pile up logs; since v12 a piece is handed out only within 64 pieces of the oldest one still being parsed, and all 11 of v12's board runs read 16.8 to 17.8 MB. v11's code trim (which we had dropped on Nov 1 after one slow run in two) came back with the cap, and v13 cut S from 466 to 447.
- **B v12 (S 1,540): the term table on a 2 MiB huge page.** Every token probes this table. We had tried huge pages before and seen nothing, because our own rule of switching transparent huge pages off for the whole process (to save memory) had already disabled them. Building and populating the table first and only then switching them off made v12 faster than v11 in 3 of 3 paired sessions (89.2 against 92.5 ms on average: run-a459624accea, run-ee38559b265b and run-59ac1f49db7f against run-01512e5d22b4, run-4448b86a7d90 and run-f7e65e70d909).
- **C v15 (S 600): hash-identified names and one shared bit matrix.** A name is identified by a 62-bit hash (three AES-NI rounds) and the distinct (country, name) pairs are one country-by-name-id bit matrix set with `lock bts`, on huge pages. This replaces v13's exact name table, per-record pair arenas and second phase: M fell from 16.2 to about 11.8 MB and S from 755 to 600 with T about 2 ms lower (K 32.5 to 37.4 on the board, medians of 9 v13 and 2 v15 runs from the same sessions; every run ID is in [`track-c/PERF.md`](track-c/PERF.md), "Box runs of the last round"). The price is a hash risk (see Correctness).

**Second wave (final pushes: f9f4afd at 11:46 UTC for A, B and D; f929929 at 12:11 UTC for C)**

- **A v14 (S 484): percentiles by a radix select.** The three chained quickselects were 9.4% of v13's instructions. For groups of more than 64 values a log-scaled key and one histogram now give each rank's bin, and only the three bins are selected inside: 705 M to 666 M instructions (-5.5%, local cachegrind), S 447 to 484. The box did not separate v14 from v13 clearly, in a noisy period: run-601a6a2c1a8c (24.1 ms, 17.3 MB, K 44.20) against run-682954fdef79 (v13, 26.1 ms, 18.8 MB, K 42.27); run-f02970944525 (19.5 ms, 17.3 MB, K 49.11) against run-f764e971bd78 (v13, 20.1 ms, 17.0 MB, K 49.12). The final pushes' runs are run-be6b2041d9b7 (19.3 ms, 17.3 MB, K 49.32) and run-7c876b605dbe (19.8 ms, 17.4 MB, K 48.73). We adopted it on the instruction count and the quiet pair; none of its four runs beats v13's best K (49.61, run-c0023c08eb4f).
- **B v13 (S 1,491): a smaller source.** v12 less 49 lines, same output, instructions -1.2%. The box cannot tell it from v12: four paired runs gave 88.5/88.8, 95.7/89.8, 89.7/108.2 and 101.9/88.2 ms (v13/v12; run IDs in [`track-b/PERF.md`](track-b/PERF.md), step 25), means 93.95 and 93.75 ms, inside v12's own spread of 87.3 to 108.2 ms. It was adopted on instructions and size, not on a measured gain in T. The final pushes' runs were run-39dd151ec1b7 (86.4 ms, 38.0 MB, K 36.72, our fastest B run) and run-34a8a8288297 (87.7 ms, 38.2 MB, K 36.43).
- **C v16 (S 609): three instruction cuts in the join.** The matrix bit is kept as one pair index, a group's min and max are two predicted branches, and a table hit is read unchecked: -3.06% instructions against v15 for 9 more lines (v15's design, limits and 62-bit identity unchanged). Local only: profile-guided optimisation on B and C (wall -1.2% and -2.0%, inside noise, S +7 each); a B fast start-up variant (the mechanism it targeted, the time to the first scan, did not move; S +36); glibc `arena_max` (a few KB); lowering the radix-select threshold below 64 values in A (instructions fall but branch mispredicts rise).

**Both waves**

- **A misattribution, corrected.** Track C's shared bitset was abandoned in v5 because a box probe that removed all name work at once was read as the cost of the atomic OR, and the v5 rewrite, which bundled several changes, was credited to its pair arenas. The shared OR costs about 2 ms in v14. [`track-c/PERF.md`](track-c/PERF.md) carries the correction.
- **Credits.** The public AVENGERS (github.com/Mukul07777/speed-demon-2026) and Cache Me (github.com/manusingh090/speed-demon-2026-entry) entries use hash-identified names and one shared country-by-name bit matrix on huge pages, and both are faster and leaner than our C. We studied them on Nov 2 and took the technique (and, from AVENGERS, the date-table hour label in A and the AES name hash and chained slot walk in C, plus some of B's size-cut ideas), and wrote our own code.
- **What the audit found.** The mistakes repeated across tracks: bundled probes and bundled rewrites that were credited to one part; single box runs inside the noise used to reject a build; rejections made on local numbers only; self-imposed rules applied too broadly (THP off for the whole process, exact name bytes, B's 44 MB memory cap treated as a wall); ignoring that M is the maximum of five runs; unverified codegen (an intrinsic that did not compile to the instruction we thought); and never reading public competitor code. Details under "How we worked".
- **Run history.** Every run in our box logs for the day (08:23 to 11:47 UTC) is ok, and the public run history has no not-ok run on Nov 2 as of its last read (see Red runs).

### Reading the numbers: the box, the laptop and board noise

- **The box is slower than our laptop, by a different factor for each kind of work.** About 1.45x on Track D, about 1.6x on Track C, and 1.9x on Track A's v7 (24.5 ms on the box against a 13.1 ms local median). Scan-bound work transfers (Track C's block scan: 1.1x); per-record work costs 2 to 3 times more on the box (2.5 GHz, turbo off, smaller caches). Sources: [A](track-a/PERF.md), [C](track-c/PERF.md), [D](track-d/PERF.md).
- **Board noise.** Repeated runs of one build differed by at most 3.5% on Track A's v8 (excluding one outlier set aside in its PERF), by 11% on its v9 (19.3 to 21.4 ms over 27 runs at S 521) and by 5% on Track D's final code over its five runs of Nov 1 (140.4 to 147.9 ms). That last figure was too good: D's 28 runs of Nov 2 ran 141.0 to 165.4 ms (K 23.35 to 25.26), and B's v12 ran 87.3 to 99.0 ms in 11 of its 12 runs with an ID and 108.2 ms in the twelfth (run-0c7664bbc162). Track A's v12 ran 19.7 to 19.9 ms in 7 of 11 runs and 20.3 to 26.9 ms in the other four, with memory 16.8 to 17.8 MB in all 11: the cap fixed the memory spikes, not the occasional slow run. Track A's v13 ran 19.6 to 20.5 ms in 6 of its 7 runs with an ID and 26.1 ms in the seventh, in the session where v14's candidate ran 24.1 ms too. Some builds also spike in time: Track A's v10 ran 22.3 to 31.2 ms on 4 of 10 runs and 19.5 to 20.8 ms on the other six, which is why we did not ship it although its best run had the track's highest K. Early, loaded runs spread more: up to 17% on Track D's v1 (156.0, 166.5 and 181.9 ms). Differences of a few percent between two builds are therefore not evidence either way; we decided on reruns and on head-to-head pairs, and on Nov 2 on at least three pairs per question.
- **Which numbers are which.** Board figures carry a run ID. Anything labelled "local" in the READMEs and PERF files was measured on our laptop and only chose candidates.

| A · Ingest | 3.1M log lines → per-hour, per-endpoint counts, p50/p95/p99 and 5xx rate | [`track-a/`](track-a/) | Eleven workers read 128 KB pieces with `pread`, turn each line into a 4-byte record in its hour's log, and report each hour while parsing; an hour is reported only after every piece that could write it is parsed, a piece is handed out only within 64 pieces of the oldest one still being parsed (so a stalled thread cannot make the others pile up memory), percentiles come from rank counting for up to 64 values and a histogram radix select above, and a line that arrives for an hour already closed makes the job rerun |
| B · Index | 50,000 boolean and phrase queries over a 250 MB corpus | [`track-b/`](track-b/) | Index only the terms that appear in `queries.txt`, in a lock-free table that sits on a 2 MiB huge page; phrases are checked during the scan at a rare anchor term (no positions stored), postings are built per 14 MB segment, and one task queue keeps all 12 threads busy |
| C · Join | Hostile CSV (quotes, embedded newlines, CRLF, BOMs) joined to a lookup table | [`track-c/`](track-c/) | AVX2 bitmask CSV parser (prefix-XOR quote mask) over 64 KiB `pread` pieces, chunk cuts guessed and then verified by quote parity, and names identified by a 62-bit hash (three AES-NI rounds, no name bytes stored) in a read-mostly lock-free table; the distinct counts are one shared country-by-name-id bit matrix set with `lock bts`, the table and matrix on three huge pages, with no per-record logs and no second phase |
| D · Traverse | 2,000 shortest-path queries on a 5M-edge weighted digraph | [`track-d/`](track-d/) | Bucketed parallel CSR build without atomics and 4-byte edges, BFS renumbering for cache locality, then bidirectional Dijkstra with a radix heap on 12 threads |

Every track folder holds what the rules ask for: `Dockerfile`, `.speed-demon.toml`, `README.md` (approach, dependencies, next 24 hours), `PERF.md` (the optimisation log, with live-board run IDs) and the source.

## Correctness

Speed that is wrong scores zero, and the final data is a seed we have never seen.

- **A root test suite.** `tests/` holds 33 end-to-end cases over all four tracks (A 7, B 9, C 9, D 8): the spec's worked examples, the official edge-case constants, tiny seeds 1 and 2 against the reference's output, and five malformed C inputs that must exit 1. `bash tests/run.sh` builds each track's image and runs every case as the scoring harness does (no network, read-only root, user nobody, pinned CPUs), comparing the output byte for byte. All 33 passed on the tree of commit f9f4afd (33 of 33 at 11:46 UTC). Track C's source changed after that, in f929929 (back to v15's layout with three instruction cuts); its 9 cases were not re-run on that commit, which the seed and fuzz gates of its row 52 stand in for. It is small by design; the heavy checks below live in each track's `PERF.md`.
- **Unseen seeds.** Full-size seeds beyond the public one, tiny and sample seeds, and the spec's own worked examples.
- **Adversarial, spec-valid inputs.** Hand-written edge cases and hostile files: shuffled, reversed and late-line logs, huge records, records longer than a read buffer, malformed lines the reference also rejects.
- **Every fallback forced.** A's rerun, B's segment splitting, C's single-chunk reparse, D's 64-bit retry were each triggered on purpose and produced the right bytes.
- **A holdout-safety audit.** We listed every fixed limit in all four programs and checked it against what the spec guarantees for any seed; Track B had one limit that was only safe in practice (at most 65,536 documents per segment), and it now holds for any valid input.
- **A concurrency audit.** We wrote down the publication protocol of every shared structure in Tracks A, B and D (A's v8 endpoint table, hour logs and speculative count check; B's lock-free term table and task queue; D's thread team, BFS claim ids and per-thread searches) and argued each one correct. Then we stress-tested them: 5,200 runs of the real images on seeds 1, 7, 101 and 202, plus 3,000 runs of copies with random sleeps and yields injected inside the suspected race windows (2,200 on A, 450 on B, 350 on D). 0 wrong outputs, crashes or hangs. Track C's v4 protocol is covered by the race fix below and 450 stress runs of the fixed build. The new B and C designs (v5.1 and v5.2) then passed a fresh concurrency review with 2,400 stress runs plus 500 race-injection runs, 0 wrong. The later rounds changed speed, not protocols, except in A: v9 closes an hour before reporting it instead of counting records, which passed 57 cases (shuffled, reversed, late and crowded-hour files among them), seeds 1, 7, 101 and 202, and 0 bad in 300 runs of seed 1 and 100 of seed 7; every later candidate repeated those gates, and B's also run under `valgrind --fair-sched`, which reproduces a lock-order deadlock that native runs almost never show (found and fixed in a development build, before any candidate was boxed).
- **Gates on Nov 2's builds.** Every candidate but A's v13 size cut (seeds 1 and 7 only, below) repeated the full-size seeds 1, 7, 101 and 202 byte for byte before it was boxed. A's cap (v12): the 52-case local set, 5 adversarial files, the late, shuffled and crowded-hour files, stress runs 0 wrong in 300 (seed 1) and 100 (seed 7), and 0 wrong in 80 runs with two CPU hogs; that size cut, which changes no behaviour, was re-checked on seeds 1 and 7 (3 runs each) and nothing wider; A's v14 radix select passed an equivalence test against the old selection on about 210,000 generated vectors and then the full A gates. B's huge-page table (v12): fuzz 23 of 23 on the normal build and on 3 stress builds, stress 0 wrong in 300 and 100; B's v13 repeated seeds 1, 7, 101 and 202 and stress 0 wrong in 100 (the final commit changes comments and two local names only). C's v16 (round 2): seeds 1, 7, 101 and 202 byte-identical, fuzz 49 of 50 at 12 and at 1 CPUs, 7 of 7 malformed inputs exit 1, 300 mutated and 300 odd-number inputs identical to v15, stress 0 wrong in 300 (seed 1) and 100 (seed 7). C's v14: release and debug builds on four seeds, fuzz 49 of 50 (the 50th, with 164,000 distinct names, exits 1 by design), 7 malformed inputs exit 1, 300 mutated and 300 odd-number inputs identical to the parent, forced single-chunk and long-name paths, a matrix self-check, stress 0 wrong in 300, 100 and 100 (the last on three CPUs); c15 (v15) repeated those with 300 runs of seed 1 and 100 each of seeds 7, 101 and 202 and on three CPUs. The residual risk we found in A's cap is a memory mode about 3 MiB higher, from the in-order writer, in about a quarter of capped runs on our laptop (local; it did not show in the 11 board runs of v12).
- **Hash identity and limits in Track C (v14 to v16).** Two different names count as one only if all 62 bits of their hashes agree (15 bits pick the bucket, 47 are stored as the tag): about 1.1e-9 per dataset for the spec's 100,000 names, if the hash is well mixed. v16 exits 1 above about 130,000 distinct names or 255 countries; the generator writes at most 100,001 names and 240 countries. That is a model, not a proof; the hash is fixed and unseeded, so a collision would fail all five final runs, not one. Evidence: seeds 1, 7, 101 and 202 byte-identical to the exact v13, six more full-size seeds (7001 to 7006) from the C correctness review, each identical to the reference, and a harness over 7.79 million structured names (trailing-space twins, one- and two-position variants of bases of 20 to 96 bytes) with 0 collisions on the 62 bits. The build needs AES-NI and PCLMULQDQ (compile-time flags; the scoring box's CPU has both) and stops with an illegal instruction, not a wrong answer, on a CPU without them. Details in [`track-c/PERF.md`](track-c/PERF.md), "Hash identity and limits".
- **One known divergence.** Track C rejects a quoted amount (`"12.50"`) with exit 1, where the reference accepts it. The generator never quotes an amount (spec 2.2), so it cannot occur in the scored inputs.
- **Fail loudly.** We accepted a few dozen extra lines per track (S rose by 18 to 49) so that an input the generator never writes fails with a clear message and exit 1 instead of a panic or a wrong answer; this is the one place we spent K on purpose.
- **The one real bug our own stress testing caught.** Track C's v4 had a 1-in-100 publication race in its lock-free name table: a slot's hash word briefly overwrote its `meta` word, so another core could take the slot for a published one of a different length and insert the same name twice, which changed one distinct count by one. A 300-run stress test of the submitted image found it, and the fix was one line (write only the three name words). It matters because final scoring needs all five runs correct: at 1 in 100 that is about a 5% chance of a zero. The board showed it once, on a v3 run that shares the same code (see Red runs); we had not linked that run to the race until later. Details in [`track-c/PERF.md`](track-c/PERF.md). Track C's v14 and v15 no longer have that table: they identify names by hash and have no per-name insert to race on, and their one shared word per slot changes once by compare-and-swap.
- **Judge-style reviews.** We reviewed each track against the official criteria (code quality, technique, optimisation log), fixed what came up, and re-verified before every push. On Nov 2 a code-quality review, a correctness attack and a `PERF.md` review of C and A produced comment, `SAFETY`-note and documentation fixes only on A and C (no code line changed after their box runs); the scores those panels gave are our own and not evidence, so we do not quote them.

## How we worked

- **Rust with zero dependencies.** Standard library plus a few hand-declared libc calls, so D = 1 and the code stays short.
- **Every speed decision settled on the scoring box.** Our laptop and the box disagree (see above): several changes that were 20 to 25% faster locally were no faster there. Local timings only chose candidates; board runs decided.
- **Box ablation probes.** The board records time and memory even when the output is wrong, so we pushed deliberately incomplete builds (read the file only, parse without the name table, build the graph without the queries). They fail the hash on purpose and are the red runs above. Subtracting their times gave the cost of each phase on the real machine.
- **Correct head-to-head candidates after that.** Once a question was answered we stopped probing and compared complete, correct builds back to back (for example `pread` against `mmap` in Track A: 24.5 ms down to 20.7 ms).
- **Second-round redesigns on B and C, each judged head to head on the box:** B 186 → 113.6 ms, C 48.5 → 32.4 ms. A day of small steps took B to 91.4 ms (v11) and C to 26.8 ms (v13); on C, T tracked the instruction count at about 12 ms per billion instructions, which predicted the box result of v6 within 0.3 ms. Nov 2's changes came from a third design round on the same two tracks plus A's memory fix (see the section at the top).
- **A fast run is not a steady build, and a slow one is not a bad build.** On Nov 1 we kept the build whose slowest run was close to its fastest: Track A's v10 and v11 had runs as fast as v9's but also ran 25 to 31 ms in 4 of 13 board runs, and v9 had none over 21.1 ms in 12. Nov 2 showed the limit of that rule. v9 also had memory spikes (21 to 22 MB in 5 of 27 runs), v11's slow run most likely had the same cause as v9's (a stalled frontier, not the trimmed code), and v11 plus the cap (v12), later cut (v13) and given the radix select (v14), is what we ship.
- **We rejected faster builds when they cost more than they earned.** The formula penalises code size and memory, so a build that gained 2 to 3% in T but added 100 lines or a few MB lost K. Track D's one-parse build (140.3 ms, S 551 to 662) and its page-fault-reduction builds (about 2 to 3% faster, +2.5 MB and S 589 to 609) were dropped for that reason, as were Track C's owner-partitioned names (20 to 25% faster locally, no faster on the box, S 889) and its half-load name table (faster, but about 7 MB more).
- **Lessons from Nov 2's rejection audit.** We went back through every rejected idea and found the same few mistakes:
  - *Probe and rewrite one thing at a time.* Track C's name probe removed all name work at once, and we blamed the one part (the atomic OR) we feared. Its v5 rewrite changed several things together and was credited to its pair arenas. The shared bitset that v5 abandoned came back in v14 as a bit matrix, and the atomic OR costs about 2 ms there, not the 21 ms we had blamed on it.
  - *One box run inside the noise is not a rejection.* Builds were dropped on a single or a pair of runs (A's v11, on one slow run in two) when the box spread was larger than the effect. Nov 2's adoptions used three or more interleaved pairs, with the production build run between the candidates.
  - *Scope your own rules.* "Transparent huge pages off for the whole process" and "name bytes must be exact" were sound where we made them and wrong when applied to a table that benefits from huge pages (B) or to the identity of a name (C). B's 44 MB point (the reference's memory over 50, where the M term stops paying) was treated as a wall: a global-evaluation design that needed 51 to 53 MiB was dropped on an estimate of its K cost (2.5 to 3.3%) and never measured, although v8 had already shown that 3 MB of headroom could buy 4% of T.
  - *Count what the score counts.* M is the maximum of five runs, not the median; we had compared A builds on median T and typical M and so missed a spike that costs about 1 point, over twice what the whole S trim of v9 to v11 is worth (about 0.4).
  - *Read the disassembly.* In the first C prototype the atomic OR compiled to a compare-and-swap loop, and the audit found that an earlier prefetch-for-write experiment (Track C's `PERF.md`, rows 22 and 31) had been judged without checking that the instruction we meant was the one emitted. C's v14 and v15 were checked with `objdump` for the one `lock bts` and one `prefetchw` they are meant to contain. We also never read the public entries that had solved the shared-bit-matrix problem until Nov 2.

## How it is scored

K = (T_ref/T)^0.50 × min(M_ref/M, 50)^0.20 × min(S_ref/S, 1)^0.15 × (D_ref/D)^0.15. Wall time dominates and is uncapped. Memory pays up to 50× less than the reference. Source lines and dependencies can only cost. The final score runs the submission five times and takes the mean of the middle three times and the **maximum** of the five memory peaks (`harness/run_submission.py`), so a memory spike in one run counts in full and a slow run in one is absorbed. That shaped every decision here: zero crates (D = 1), no needless copies of the input (Tracks A, B and C read it in cache-sized pieces with `pread`; Track D memory-maps it), short code, and, since Nov 2, a bound on the worst-case memory of a run as well as its typical case.

## How to verify a change

`check.py` is the organisers' checker from the starter template. `bench/bench.sh` is our stricter local stand-in for the scoring harness: the same sandbox flags, cores 0-11, a warmed page cache, and the run's cgroup `memory.peak`, with a sha256 check of the output. `bench.sh` holds the seed-1 hashes; pass `EXPECT_SHA` for any other seed.

```sh
# 1. Generate the data with the public generators (seed 1 is the board's dataset)
git clone https://github.com/hackathon-raptors/speed-demon-2026 ../sd-official
python3 ../sd-official/generators/a_ingest.py --seed 1 --scale full --out data/a   # likewise b, c, d

# 2. Load it into the docker volume `sd-data`: subdirs a..d for seed 1, s7-a..s7-d for seed 7
docker run --rm -v "$PWD/data:/src:ro" -v sd-data:/data \
  debian:13-slim@sha256:62bd423aeee912639ca8ee681c2b762cb3e25137e0a92b20be455898a9f034ad \
  sh -c 'mkdir -p /data/a && cp /src/a/* /data/a/'      # repeat with b, c, d; for seed 7 copy a seed-7 tree to /data/s7-a ...

# 3. Correctness: the end-to-end suite (33 cases, all four tracks; needs docker), then the organisers' checker
bash tests/run.sh            # or: bash tests/run.sh c d
python3 check.py a --data data/a

# 4. Timing, memory.peak and output sha, five runs, seed 1
bash bench/bench.sh a 5

# 5. A second seed: take the sha of the reference output for that seed
EXPECT_SHA=<sha> bash bench/bench.sh a 3 s7-a

# 6. S and D exactly as the harness counts them (needs ../sd-official and its tools image)
python3 bench/static_axes.py track-a

# 7. The live board: our runs and each track's top five, then the overall standing
python3 bench/board.py
python3 bench/overall.py
```

Replace `a` with `b`, `c` or `d` for the other tracks.
